# APM 구현 가이드 — 인프라 증설·축소 판단을 위한 관측 요구사항

이 문서는 신규 서비스에 APM(Application Performance Monitoring)을 구성할 때
**"인프라를 늘려야 하는가, 줄여도 되는가, 무엇을 늘려야 하는가"** 를 데이터로 판단할 수 있게
만들기 위한 구현 요구사항입니다.

구현 담당자(사람 또는 AI 에이전트)는 이 문서의 **§1 P0 항목을 전부 충족한 뒤**,
**§8 완료 체크리스트로 스스로 검증**한 후에 완료를 보고합니다.

전제 스택은 Prometheus(수집) + Grafana(시각화)입니다. 다른 도구를 쓰더라도
요구되는 **질문과 지표는 동일**하며, 구현 방식만 달라집니다.

---

## 0. 이 시스템이 답할 수 있어야 하는 질문

구현의 성공 기준은 "지표를 만들었는가"가 아니라 **"아래 질문에 데이터로 답할 수 있는가"** 입니다.
각 질문 옆의 절에 그 답을 만드는 요구사항이 있습니다.

| # | 질문 | 관련 절 |
|---|------|---------|
| Q1 | 지금 사용자가 겪는 실패율과 지연은 얼마인가 | §1.1 |
| Q2 | 현재 부하가 인스턴스당 한계의 몇 %인가 | §1.2, §4 |
| Q3 | 지금 병목은 앱인가, DB인가, 큐인가, 외부 의존인가 | §1.3~1.6, §3 |
| Q4 | 증설한다면 **무엇을** 늘려야 하는가 | §3 |
| Q5 | 증설해도 되는가 (다른 자원 상한에 걸리지 않는가) | §1.7, §3.3 |
| Q6 | 지금 규모를 **줄여도** 되는가 | §5.2 |
| Q7 | 느린 요청의 시간은 **왜, 어디로** 갔는가 | §9 |

**Q4와 Q6이 이 문서의 존재 이유입니다.** 대부분의 모니터링 구축은 Q1에서 멈추고,
그 결과 "느리다 → 인스턴스를 늘린다"는 잘못된 반사 행동이 굳어집니다.

**Q7은 메트릭만으로는 구조적으로 답할 수 없습니다.** 메트릭은 집계된 숫자이므로
개별 요청의 내부를 볼 수 없습니다. 증설 판단(Q2~Q6)만 필요하다면 §1~5로 충분하지만,
**성능을 개선하려면 §9가 반드시 필요합니다.**

## 1. P0 — 필수 계측 (이것 없이는 완료가 아님)

각 항목에 **왜 필요한지(없으면 답 못 하는 질문)** 와 **수용 기준**을 명시합니다.
수용 기준은 검증 가능한 형태로 작성돼 있으므로, 구현 후 하나씩 확인합니다.

---

### 1.1 HTTP 요청 지표 (RED)

**없으면 답 못 하는 것**: 사용자가 지금 아픈가. 모든 판단의 출발점.

```
http_requests_total{method, route, status}          # Counter
http_request_duration_seconds{method, route}        # Histogram
```

**수용 기준**

- [ ] `route` 라벨은 **라우트 템플릿**이다. `/users/8213`이 아니라 `/users/:id`.
      프레임워크의 라우트 매칭 결과를 쓰고, 원본 URL 문자열을 쓰지 않는다.
- [ ] 지연은 **Histogram**이다. Summary를 쓰지 않는다.
      (Summary는 여러 인스턴스에 걸친 분위수 집계가 수학적으로 불가능하다.)
- [ ] 히스토그램 버킷이 **SLO 목표값 근처에 촘촘**하다.
      목표 p95가 300ms라면 `[0.05, 0.1, 0.2, 0.3, 0.5, 1, 2, 5]` 형태.
      목표값이 버킷 경계에 없으면 그 분위수 값 자체를 신뢰할 수 없다.
- [ ] 4xx와 5xx가 구분된다. 4xx는 대부분 클라이언트 문제이므로 에러율에서 분리한다.
- [ ] 미들웨어/인터셉터로 **전역 적용**된다. 엔드포인트마다 수동으로 붙이지 않는다.

---

### 1.2 동시 처리 수 (in-flight)

**없으면 답 못 하는 것**: 현재 부하가 한계의 몇 %인가 (Q2). **오토스케일의 기준 지표.**

```
http_requests_in_flight        # Gauge — 요청 시작 시 +1, 종료 시 -1
```

**왜 CPU가 아니라 이것인가**

CPU 사용률은 포화의 대리 지표일 뿐이며, I/O 대기가 지배적인 서비스에서는 어긋납니다.
Node.js·Python 같은 런타임은 CPU 30~40%에서 이미 포화 상태일 수 있고,
반대로 배치성 작업은 CPU 90%에서도 건강합니다.
**동시 처리 수는 "얼마나 많은 일을 동시에 떠안고 있는가"를 직접 측정**하므로 런타임 특성에 덜 휘둘립니다.

Gauge를 직접 두지 못하는 환경이라면 Little's Law로 유도할 수 있습니다.

```
평균 동시 요청 수 = 요청률(RPS) × 평균 응답시간(초)
```

```promql
sum(rate(http_requests_total[5m]))
  * sum(rate(http_request_duration_seconds_sum[5m]))
    / sum(rate(http_request_duration_seconds_count[5m]))
```

다만 **직접 측정하는 Gauge를 우선**합니다. 유도값은 평균에 의존해 순간 폭증을 놓칩니다.

**수용 기준**

- [ ] 요청 실패·예외 발생 시에도 감소가 보장된다 (`finally` 계열로 처리).
      누락되면 값이 단조증가하며 영원히 잘못된 값을 보고한다.
- [ ] `http_requests_in_flight / 인스턴스 수` 값을 Grafana에서 조회할 수 있다.

---

### 1.3 런타임 포화 신호

**없으면 답 못 하는 것**: 병목이 앱 자체인가 (Q3).

런타임마다 **포화가 드러나는 지점이 다릅니다.** 사용 런타임에 해당하는 것을 계측합니다.

| 런타임 | 필수 지표 | 포화 신호 |
|---|---|---|
| Node.js | 이벤트 루프 lag (p99), heap 사용량, GC duration | lag p99 상승 = 단일 스레드가 막힘 |
| JVM | GC pause·빈도, 힙 사용률, **스레드풀 큐 깊이** | 큐 깊이 증가 = 워커 부족 |
| Go | goroutine 수, GC pause, 스케줄러 지연 | goroutine 급증 = 블로킹 누적 |
| Python | 워커별 활성 요청, 워커 큐 대기 | 큐 대기 = 워커 부족 |

**수용 기준**

- [ ] 해당 런타임의 표준 익스포터/기본 수집기를 활성화했다
      (예: `collectDefaultMetrics`, Micrometer JVM binder, `promhttp` 기본 컬렉터).
- [ ] 위 표의 "포화 신호" 지표를 Grafana 패널로 노출했다.

---

### 1.4 커넥션 풀 대기 — **가장 자주 빠지고, 가장 중요한 항목**

**없으면 답 못 하는 것**: **앱을 늘려야 하는가, DB를 늘려야 하는가 (Q4).**

```
db_pool_connections_active         # Gauge — 사용 중
db_pool_connections_idle           # Gauge — 유휴
db_pool_wait_duration_seconds      # Histogram — 커넥션 획득까지 대기 시간
db_pool_pending_requests           # Gauge — 커넥션을 기다리는 요청 수
```

**왜 이것이 결정적인가**

응답이 느린데 DB CPU가 한가한 상황에서, 원인은 거의 항상 풀 대기입니다.
이때 **앱 인스턴스를 늘리면 커넥션 경합이 심해져 상황이 악화됩니다.**
올바른 조치는 풀 크기 조정이거나 쿼리 개선입니다.
이 지표가 없으면 두 상황을 구분할 방법이 없고, 증설이 장애를 키웁니다.

ORM/드라이버가 기본 제공하지 않는 경우가 많으므로 **직접 계측해야 합니다.**
"기본 제공되지 않는다"는 이유로 생략하지 않습니다.

**수용 기준**

- [ ] 풀 대기 시간 히스토그램이 존재하고, p95를 조회할 수 있다.
- [ ] 캐시·외부 API 등 다른 커넥션 풀에도 동일하게 적용했다.
- [ ] `active / (active + idle)` 풀 사용률 패널이 있다.

---

### 1.5 비동기 큐 지표 (큐·워커를 쓰는 경우 필수)

**없으면 답 못 하는 것**: 워커를 늘려야 하는가 (Q4).

```
queue_depth{queue}                    # Gauge — 미처리 항목 수
queue_oldest_item_age_seconds{queue}  # Gauge — 가장 오래된 항목의 나이
queue_processed_total{queue, result}  # Counter — 성공/실패
queue_processing_duration_seconds     # Histogram
```

**깊이보다 나이(age)가 중요합니다.** 깊이 10만이 30초분일 수도, 6시간분일 수도 있습니다.
나이는 그 자체로 "사용자가 실제로 얼마나 기다리는가"이며, 깊이는 그렇지 않습니다.

판단은 **절대값이 아니라 기울기**로 합니다.

```promql
deriv(queue_depth[10m])   # 양수 지속 = 소비가 생산을 못 따라감 → 워커 증설
```

**수용 기준**

- [ ] `age` 지표가 존재한다 (깊이만 있으면 미충족).
- [ ] 재시도 횟수와 DLQ 유입이 별도로 카운트된다.

---

### 1.6 의존 대상별 아웃바운드 지표

**없으면 답 못 하는 것**: 이게 내 문제인가, 남의 문제인가 (Q3).

```
outbound_requests_total{target, status}       # Counter
outbound_duration_seconds{target}             # Histogram
```

`target`은 외부 API, 내부 서비스, DB, 캐시 등입니다.
이것이 없으면 "우리 서비스가 느리다"까지만 알 수 있고,
외부 결제사 지연 때문인지 우리 코드 때문인지 구분할 수 없습니다.
잘못된 증설로 이어지는 대표적 경로입니다.

**수용 기준**

- [ ] 외부 의존 각각에 대해 RED 3종이 있다.
- [ ] 타임아웃과 서킷 브레이커 개방 횟수가 카운트된다.

---

### 1.7 자원 한계 지표 (증설 가능 여부 판단)

**없으면 답 못 하는 것**: 증설해도 안전한가 (Q5).

컨테이너/호스트 익스포터(cAdvisor, node_exporter, 클라우드 매니지드 지표)로 수집합니다.

```
container_cpu_cfs_throttled_seconds_total   # CPU throttling — 사용률보다 중요
container_memory_working_set_bytes / limit  # 메모리 여유
kube_pod_container_status_restarts_total    # OOMKill·크래시
```

여기에 **의존 자원의 절대 상한**을 반드시 함께 수집합니다.

```
DB 최대 커넥션 수, 현재 커넥션 수
캐시 maxmemory 대비 사용량, eviction 수
큐 파티션 수 (컨슈머 증설의 상한)
외부 API 쿼터 소진율
```

**왜 필요한가**

앱 인스턴스 수 × 인스턴스당 풀 크기 = 총 DB 커넥션입니다.
**스케일아웃이 DB 커넥션 상한을 넘기면 증설 자체가 장애가 됩니다.**
오토스케일의 최대 인스턴스 수는 이 계산에서 역산해야 합니다.

**수용 기준**

- [ ] CPU throttling 비율 패널이 있다 (사용률만으로는 미충족).
- [ ] DB 커넥션 사용률(`현재 / 최대`) 패널이 있다.
- [ ] `최대 인스턴스 수 × 인스턴스당 풀 크기 < DB 최대 커넥션 × 0.8` 계산을 문서에 기록했다.

---

### 1.8 비즈니스 지표 (최소 3개)

**없으면 답 못 하는 것**: 기술 지표가 전부 정상인데 서비스가 죽은 경우.

서비스 핵심 액션 3~5개의 시도·성공을 카운트합니다.
로그인, 가입, 주문, 결제, 콘텐츠 생성 등.

"평소 이맘때 대비 절반"이 CPU 그래프보다 먼저 사고를 알려줍니다.
많이 만들 필요는 없고, **핵심 3개면 충분합니다.**

## 2. 지표 → 판단 매핑

수집만 하고 판단에 안 쓰이는 지표는 노이즈입니다. 아래 매핑을 문서에 유지합니다.

| 판단 | 근거 지표 | 임계 기준 |
|---|---|---|
| 증설 필요 여부 | 인스턴스당 in-flight | 측정된 한계의 70% (§4) |
| 앱 증설 vs DB 증설 | 풀 대기 p95 + DB CPU | §3 결정 트리 |
| 워커 증설 | `deriv(queue_depth)`, `queue_age` | 기울기 양수 지속 10분 |
| 증설 안전성 | DB 커넥션 사용률 | 80% 미만 유지 |
| 축소 가능 여부 | in-flight + p95 여유 | §5.2 |
| 긴급 대응 필요 | 에러율, p95, SLO 소진율 | §5.3 |

---

## 3. 스케일 방향 결정 트리 — 문서의 핵심

**"느리다 → 인스턴스를 늘린다"가 틀리는 경우가 절반 이상입니다.**
증설 전 아래 순서로 병목 위치를 확정합니다.

### 3.1 결정 트리

```
p95 지연이 기준선을 초과했다
│
├─ 외부 의존(outbound) 지연이 함께 올랐는가?
│   └─ YES → 외부 문제. 서킷 브레이커·캐싱·타임아웃 조정.
│            자체 인프라 증설은 효과 없음. 【증설 금지】
│
├─ 커넥션 풀 대기 p95가 올랐는가?
│   ├─ YES + DB CPU 낮음  → 풀 크기 상향 또는 쿼리 개선.
│   │                       【앱 증설 금지 — 경합 악화】
│   └─ YES + DB CPU 높음  → DB 스케일업 / 리드 레플리카 / 쿼리 개선.
│                           【앱 증설 금지 — DB만 더 죽음】
│
├─ 런타임 포화 신호(§1.3)가 올랐는가?
│   └─ YES → 앱 병목. 【앱 수평 증설】 또는 무거운 작업 비동기 분리.
│
├─ CPU throttling이 발생하는가?
│   └─ YES → 리소스 limit 상향(수직) 우선. 증설로는 해결 안 됨.
│
├─ 캐시 eviction 급증 / hit rate 하락?
│   └─ YES → 캐시 메모리 증설. DB 부하는 결과일 뿐.
│
└─ 위 어디에도 해당 없음 + in-flight가 한계 근처
    └─ 【앱 수평 증설】 (정상적인 트래픽 증가)
```

### 3.2 구현 요구사항

- [ ] 위 트리의 각 분기에 해당하는 지표가 **하나의 Grafana 대시보드에 나란히** 배치돼 있다.
      여러 대시보드를 오가야 하면 장애 중에 아무도 이 트리를 따르지 않는다.
- [ ] 대시보드 이름을 "Scaling Decision"처럼 목적이 드러나게 짓는다.

### 3.3 증설 전 안전 확인

증설을 결정한 뒤, 실행 전 확인합니다.

- [ ] 증설 후 총 DB 커넥션이 상한의 80% 미만인가
- [ ] 큐 컨슈머라면 파티션 수가 컨슈머 수 이상인가 (파티션이 상한)
- [ ] 외부 API 쿼터에 여유가 있는가

## 4. 기준선 확립 — 임계값은 측정으로 정합니다

**이 절을 건너뛰면 앞의 모든 지표가 판단 도구가 되지 못합니다.**
지표는 "몇이 정상인가"를 스스로 알려주지 않기 때문입니다.

### 4.1 절차

1. 스테이징에 프로덕션과 동일한 스펙의 인스턴스 **1대**를 띄운다.
2. 부하를 단계적으로 올린다 (예: 50 → 100 → 200 → 400 RPS, 각 5분 유지).
3. 각 단계에서 **RPS, p95 지연, in-flight, 에러율**을 기록한다.
4. x축 RPS, y축 p95로 그래프를 그린다.
5. **지연이 급격히 꺾이는 지점(knee)** 을 찾는다. 그 지점이 인스턴스 1대의 한계다.
6. knee 지점의 **in-flight 값**을 기록한다. 이것이 인스턴스당 한계 동시성이다.
7. **한계의 70%** 를 운영 기준선이자 스케일아웃 트리거로 삼는다.

### 4.2 왜 70%인가

knee 근처에서는 부하가 조금만 늘어도 지연이 비선형으로 악화되고,
그 너머에서는 경합 비용 때문에 **처리량이 오히려 감소**합니다.
따라서 "한계까지 쓰다가 늘린다"는 전략은 성립하지 않습니다.
증설이 반영되는 데 걸리는 시간(수십 초~수 분) 동안 버틸 여유가 필요합니다.

### 4.3 산출물

측정 결과를 코드와 함께 저장합니다.

```yaml
# capacity-baseline.yaml — 분기마다 재측정
measured_at: YYYY-MM-DD
instance_spec: "2 vCPU / 4GB"
knee_rps: TODO
max_inflight_per_instance: TODO      # ← 오토스케일 기준값의 근거
scale_out_threshold: TODO            # max_inflight × 0.7
p95_at_knee_ms: TODO
```

- [ ] 위 파일이 존재하고 `TODO`가 실제 측정값으로 채워져 있다.
- [ ] 오토스케일 설정이 이 파일의 값을 근거로 한다.

**측정 전에는 임계값을 숫자로 확정하지 않습니다.** 근거 없는 숫자는 잘못된 자동화를 만듭니다.

## 5. 오토스케일 연결과 축소 기준

### 5.1 스케일아웃

- [ ] 오토스케일 기준 지표는 **인스턴스당 in-flight**(또는 RPS)다. CPU 단독 사용 금지.
- [ ] 임계값은 §4에서 측정한 값이다.
- [ ] 최대 인스턴스 수는 §1.7의 자원 상한 역산으로 정했다.
- [ ] 최소 인스턴스 수는 2 이상이다 (단일 장애점 회피).

### 5.2 스케일인(축소) — 별도 규칙이 필요합니다

축소는 증설보다 위험합니다. **잘못 줄이면 즉시 장애**이고, 트래픽은 예고 없이 돌아옵니다.
따라서 증설 조건의 역이 아니라, **더 보수적인 별도 조건**을 씁니다.

- [ ] **히스테리시스**: 축소 임계값은 증설 임계값보다 확실히 낮다 (예: 증설 70%, 축소 40%).
      같은 값을 쓰면 경계에서 증설·축소가 반복되는 플래핑이 발생한다.
- [ ] **지속 시간 조건**: 조건이 **10분 이상 연속** 유지될 때만 축소한다. 순간값으로 줄이지 않는다.
- [ ] **쿨다운**: 직전 스케일 조작 후 최소 5분이 지나야 다음 축소를 허용한다.
- [ ] **한 번에 한 단계씩**: 축소는 점진적으로 한다. 증설은 여러 단계를 한 번에 해도 되지만 축소는 안 된다.
- [ ] **그레이스풀 셧다운**: 종료 시 진행 중인 요청을 완료하고 새 요청을 받지 않는다.
      이것이 없으면 축소할 때마다 에러율이 튄다.
- [ ] **주기 패턴 확인**: 일·주 단위 트래픽 그래프에서 반복 패턴이 뚜렷하면
      반응형 축소보다 **예약 스케일링**이 안전하고 저렴하다.

**비용 최적화 관점의 축소는 자동화보다 주간 리뷰가 낫습니다.**
"지난주 최대 in-flight가 한계의 20%였다"를 사람이 보고 기준 인스턴스 수를 조정하는 편이,
공격적인 자동 축소보다 사고 위험이 낮습니다.

### 5.3 알림

- [ ] **증상 기반만 사람을 호출**한다 (에러율, p95, 가용성).
      "CPU 높음" 같은 원인 기반은 사용자가 멀쩡하면 티켓으로 보낸다.
- [ ] SLO 에러 예산 **소진율(burn rate)** 기반 알림을 쓴다.
      단일 임계값(`에러율 > 1%`)은 오탐·미탐이 동시에 많다.
      빠른 소진은 즉시 호출, 느린 소진은 티켓으로 분리한다.
- [ ] 용량 관련은 **선행 알림**으로 건다.
      "포화 도달"이 아니라 "현 추세로 N시간 뒤 소진"이어야 대응 시간이 생긴다.
- [ ] `prometheus_tsdb_head_series` 급증 알림을 건다 (§6 카디널리티 사고 조기 감지).

## 6. 금지 사항

구현 시 반복적으로 발생하는 실수입니다. 명시적으로 금지합니다.

| 금지 | 이유 |
|---|---|
| 라벨에 사용자 ID·요청 ID·이메일·원본 URL·에러 메시지 넣기 | 시계열이 곱셈으로 증가해 수집 서버가 OOM으로 사망. 이 정보는 로그·트레이스로 보낸다 |

| 평균 지연만 표시 | 꼬리 지연이 완전히 감춰짐. p50/p95/p99를 함께 본다 |
| 인스턴스 집계값만 표시 | 특정 인스턴스 1대만 고장 난 상황을 구조적으로 못 봄 |
| CPU 단독 오토스케일 | I/O 바운드 서비스에서 뒤늦게 반응 |
| 부하 테스트 없이 임계값 확정 | 근거 없는 숫자로 자동화하면 잘못된 스케일링이 자동으로 반복됨 |

| 수집 서버에 `sample_limit` 미설정 | 앱 하나의 실수가 모니터링 전체를 무너뜨림 |

수집 서버 보호 설정을 함께 넣습니다.

```yaml
scrape_configs:
  - job_name: app
    sample_limit: 50000            # 타깃 하나의 샘플 상한 (회로 차단기)
    label_limit: 30
    label_value_length_limit: 200
```

## 9. 성능 진단 계층 — 메트릭이 답할 수 없는 것

§1~5의 메트릭은 **"문제가 있는가, 어느 계층인가, 늘려야 하는가"** 까지만 답합니다.
메트릭은 집계된 숫자이므로 **개별 요청의 내부를 볼 수 없고**, 이는 계측 부족이 아니라 설계 한계입니다.

성능 **개선**이 목표라면 아래 도구가 추가로 필요합니다.

| 도구 | 답하는 질문 | 상시 여부 |
|---|---|---|
| 메트릭 (§1~5) | 문제가 있는가, 어디쯤인가, 늘려야 하는가 | 상시 |
| **분산 트레이싱** | 이 요청의 시간이 어느 구간으로 갔는가 | 샘플링 |
| **느린 쿼리 수집** | 어느 쿼리가 비싼가, N+1인가 | 상시(임계 초과분) |
| 컨티뉴어스 프로파일링 | 어느 코드가 CPU·메모리를 먹는가 | 저빈도 샘플링 |
| 로그 | 이 케이스에 정확히 무슨 일이 있었는가 | 상시 |

---

### 9.1 분산 트레이싱

**없으면 답 못 하는 것**: p95가 800ms인데, 그 800ms가 어디로 갔는가.

**필수 span (이보다 적으면 진단 가치가 없음)**

```
HTTP 서버 요청 (루트 span)
├─ 인증·인가 처리
├─ DB 쿼리        ← 개별 쿼리마다 별도 span, 쿼리 텍스트를 속성으로
├─ 캐시 조회
├─ 외부 API 호출
└─ 큐 발행
```

**수용 기준**

- [ ] DB 쿼리가 **개별 span**으로 잡힌다.
      "DB 호출 전체 200ms"가 아니라 "쿼리 A 5ms × 40회"가 보여야 N+1을 발견할 수 있다.
      이것이 트레이싱을 넣는 가장 큰 이유다.
- [ ] 쿼리 텍스트는 **파라미터가 제거된 형태**로 기록된다 (`WHERE id = $1`).
      실제 값이 들어가면 개인정보 유출이자 카디널리티 문제가 된다.
- [ ] 서비스 간·큐 경계를 넘어 **trace context가 전파**된다.
      HTTP는 `traceparent` 헤더, 큐는 메시지 헤더에 실어 보낸다.
- [ ] 비동기 워커의 처리도 원 요청의 트레이스에 연결된다 (링크 또는 자식 span).

**샘플링 전략**

전량 수집은 비용과 성능 양쪽에서 불가능합니다. 그러나 **단순 확률 샘플링은 함정**입니다.
1% 샘플링을 하면 정작 보고 싶은 느린 요청과 에러가 대부분 버려집니다.

- [ ] 정상 요청은 낮은 비율(1~5%)로 샘플링한다.
- [ ] **에러 요청과 임계 시간 초과 요청은 100% 수집**한다.
      Tail-based sampling(요청 종료 후 판단)을 쓰거나, 최소한 에러 시 강제 샘플링 플래그를 세운다.
- [ ] 샘플링 결정은 루트에서 내리고 전체 트레이스에 전파한다 (조각난 트레이스 방지).

---

### 9.2 exemplar 연결 — 투자 대비 효과가 가장 큰 항목

**메트릭 그래프에서 트레이스로 바로 점프하는 연결**입니다.

히스토그램 버킷에 그 구간을 만든 실제 요청의 trace ID를 함께 저장하면,
Grafana에서 **p99가 튄 지점을 클릭 → 그 느린 요청의 트레이스**로 이동합니다.

이것이 없으면 "p99가 800ms"에서 "어떤 요청이 그랬는지"를 찾는 데 로그를 뒤져야 하고,
실무에서는 결국 추측으로 끝납니다. **메트릭과 트레이싱을 잇는 다리이므로 둘 다 있다면 반드시 연결합니다.**

- [ ] 지연 히스토그램에 exemplar가 붙는다.
- [ ] Grafana에서 그래프의 exemplar 점을 클릭하면 트레이스가 열린다.
- [ ] Prometheus는 exemplar 저장 옵션이 켜져 있다 (기본 비활성).

---

### 9.3 컨티뉴어스 프로파일링

**없으면 답 못 하는 것**: 어느 함수가 CPU를 먹는가, 어디서 메모리가 새는가.

트레이싱은 **span 사이의 시간**을 못 봅니다. "DB도 외부 API도 빠른데 요청이 느리다"면
답은 애플리케이션 코드 안에 있고, 이건 프로파일러만 볼 수 있습니다.

- [ ] 낮은 빈도(수십 Hz)로 상시 프로파일을 수집한다. 문제 발생 후 붙이면 이미 늦다.
- [ ] CPU와 힙 양쪽을 수집한다.

P2로 두어도 되지만, **메모리 누수나 원인 불명의 CPU 상승이 한 번이라도 발생하면 즉시 P1로 올립니다.**

---

### 9.4 DB 쿼리 레벨 수집

**없으면 답 못 하는 것**: 어느 쿼리를 고쳐야 하는가.

- [ ] 쿼리별 누적 통계(실행 횟수, 총·평균 시간, 반환 행 수)를 수집한다.
- [ ] 임계 시간을 넘는 쿼리를 로그로 남긴다.
- [ ] 총 시간 상위 쿼리 목록을 대시보드나 정기 리포트로 노출한다.

**평균이 느린 쿼리보다 "빠르지만 너무 자주 호출되는 쿼리"가 실제 병목인 경우가 많습니다.**
따라서 정렬 기준은 평균 시간이 아니라 **총 소요 시간(평균 × 호출 수)** 입니다.

## 10. 스택별 구현 예시 — Node.js + PostgreSQL + ECS

아래는 구체적 스택 예시입니다. 다른 스택이라면 §1~9의 요구사항은 그대로 두고
이 절만 교체합니다.

### 10.1 Node.js

**메트릭**

- `prom-client`의 기본 수집기를 켠다. 이벤트 루프 lag, heap, GC가 자동으로 수집된다.
- **이벤트 루프 lag p99가 Node.js의 핵심 포화 신호다.** CPU 사용률이 낮아도
  lag이 올라가면 이미 포화이며, 이 경우 §3 결정 트리는 "앱 수평 증설"로 간다.
- 단일 스레드이므로 **한 인스턴스의 CPU 코어를 여러 개 줘도 대부분 놀게 됩니다.**
  ECS task에 vCPU를 늘리는 것(수직)보다 task 수를 늘리는 것(수평)이 대체로 유효하다.
  (클러스터 모드를 쓰지 않는 한 그렇다.)

**트레이싱**

- OpenTelemetry Node SDK + 자동 계측을 쓴다. HTTP 서버/클라이언트와
  `pg` 드라이버 계측이 포함되므로, **쿼리별 span이 코드 수정 없이 얻어진다.**
- ORM을 쓴다면 ORM 계층이 아니라 **드라이버 계층 계측을 확인한다.**
  ORM에서만 잡으면 실제 발행된 쿼리 수를 못 보고, N+1 발견이라는 목적이 무너진다.
- `prom-client`는 exemplar를 지원하므로 §9.2 연결이 가능하다.

**주의**

- 자동 계측은 span을 많이 만든다. 처음에는 HTTP·DB·외부 호출만 켜고 시작한다.
- 프로파일링은 상시 저빈도 수집을 쓴다. `--cpu-prof` 같은 일회성 도구는
  문제가 재현될 때만 쓸 수 있어 상시 관측을 대체하지 못한다.

### 10.2 PostgreSQL

**필수 설정**

- `pg_stat_statements` 확장을 활성화한다. §9.4의 쿼리별 통계가 여기서 나온다.
  **이것 없이는 어느 쿼리를 고칠지 알 수 없다.**
- `log_min_duration_statement`로 느린 쿼리 로그 임계값을 설정한다 (예: 500ms).
- `auto_explain`을 켜면 느린 쿼리의 실행 계획까지 자동 기록된다.

**메트릭 (postgres_exporter)**

| 지표 | 판단 |
|---|---|
| 커넥션 사용률 (`현재 / max_connections`) | 증설 안전성 (§1.7) |
| `xact_commit` / `xact_rollback` 비율 | 트랜잭션 처리량, 롤백 급증 |
| 락 대기 수, 최장 트랜잭션 나이 | 락 경합 — 증설로 해결 안 되는 유형 |
| 캐시 히트율 (`blks_hit / (blks_hit + blks_read)`) | 메모리 부족 → 수직 증설 신호 |
| replication lag | 리드 레플리카 사용 가능 여부 |
| 데드 튜플 수, autovacuum 지연 | 방치 시 성능이 서서히 무너짐 |

**커넥션 폭발 — ECS 조합에서 반드시 계산할 것**

```
총 커넥션 = ECS task 수 × task당 풀 크기
```

오토스케일로 task가 4개에서 40개로 늘면 커넥션도 10배가 됩니다.
**RDS의 `max_connections`는 인스턴스 클래스에 종속되므로 쉽게 한계에 닿습니다.**
스케일아웃이 그대로 DB 장애가 되는 전형적 경로입니다.

- [ ] `최대 task 수 × task당 풀 크기 < max_connections × 0.8` 을 계산해 기록한다.
- [ ] 이 부등식이 성립하지 않으면 **커넥션 풀러(RDS Proxy, PgBouncer)를 도입**하거나
      최대 task 수를 그에 맞게 제한한다.
- [ ] 풀러를 도입한 경우, 풀러 자체의 대기 지표도 §1.4에 포함한다.

### 10.3 ECS 특화

**(a) 서비스 디스커버리 — 정적 타깃 설정이 불가능하다**

ECS task는 배포·스케일마다 IP가 바뀌고 수시로 생사가 갈립니다.
Prometheus의 `static_configs`로는 관측이 불가능합니다.

- [ ] ECS 서비스 디스커버리를 사용한다. 수집기가 task를 자동 발견해야 한다.
- [ ] task 종료 시점의 마지막 지표가 유실되지 않도록 수집 주기와 종료 대기 시간을 맞춘다.
      (수집 주기 15초라면 종료 유예가 그보다 길어야 마지막 구간이 남는다.)

이 문제 때문에 **ECS에서는 수집기를 사이드카나 데몬 형태로 두고,
task가 자기 지표를 밀어내는(push) 구성이 pull보다 안정적인 경우가 많습니다.**
어느 쪽이든 "짧게 살고 사라지는 task"를 전제로 설계합니다.

**(b) 오토스케일 지표 선택**

ECS Service Auto Scaling에서 실용적인 선택지는 셋입니다.

| 방식 | 평가 |
|---|---|
| CPU 사용률 target tracking | **비권장.** Node.js에서 포화를 늦게 반영 |
| **ALB `RequestCountPerTarget`** | **권장.** 별도 계측 없이 얻어지고, 부하와 직접 연동 |
| 커스텀 지표 (task당 in-flight) | 가장 정확. §1.2를 CloudWatch로 내보내야 함 |

**`RequestCountPerTarget`이 현실적인 기본값입니다.** §4의 부하 테스트에서
"task 1대가 감당하는 RPS"를 측정했다면 그 값의 70%를 목표치로 설정하면 됩니다.
in-flight 기반이 더 정확하지만 지표를 CloudWatch로 내보내는 비용이 붙으므로,
정확도가 실제로 부족하다고 판명될 때 넘어갑니다.

**(c) 자원 지표**

- ECS task metadata 엔드포인트에서 task 단위 CPU·메모리 사용량을 얻는다.
- **Fargate는 cgroup throttling 지표를 직접 노출하지 않는다.**
  §1.7의 CPU throttling 항목은 EC2 launch type에서만 온전하며,
  Fargate에서는 "CPU 사용량이 할당량에 붙어 있는가"로 대체 판단한다.
- 메모리는 hard limit 초과 시 즉시 OOMKill이다.
  **재시작 횟수를 반드시 알림으로 건다.** 메모리 누수가 조용히 진행되다가
  주기적 재시작으로 가려지는 상황이 흔하다.

**(d) 그레이스풀 셧다운 — §5.2 축소 규칙의 전제**

이것이 없으면 **스케일인할 때마다 에러율이 튑니다.** 축소를 자동화할 수 없게 됩니다.

순서를 맞춰야 합니다.

```
1. ALB 대상 그룹에서 등록 해제 (deregistration delay 동안 새 요청 차단)
2. ECS가 SIGTERM 전송
3. 앱: 새 요청 수신 중단 → 진행 중 요청 완료 → 커넥션 정리 → 종료
4. 유예 시간 초과 시 SIGKILL
```

- [ ] 앱이 SIGTERM을 처리해 진행 중 요청을 완료한다.
- [ ] ECS `stopTimeout`이 **최장 요청 처리 시간보다 길다.**
- [ ] ALB deregistration delay가 요청 처리 시간을 커버한다.
- [ ] 헬스체크가 종료 시작 즉시 실패를 반환해 새 트래픽이 끊긴다.
- [ ] 축소 시 5xx가 증가하지 않음을 실제로 확인했다 (§8 검증 시나리오).

**(e) ALB 지표 — 엣지 계층**

앱 내부 지표는 **앱에 도달한 요청만** 셉니다. 커넥션 큐에서 죽거나 ALB가 직접 5xx를
반환한 요청은 앱 지표에 존재하지 않으므로, 사용자가 겪은 실제 실패율은 ALB에서만 보입니다.

- [ ] `TargetResponseTime` — 앱 측정값과 비교. 차이가 크면 큐잉이 일어나고 있다.
- [ ] `HTTPCode_ELB_5XX_Count` — **앱 지표에 안 잡히는 실패**
- [ ] `RejectedConnectionCount` — 커넥션 한계 도달
- [ ] `UnHealthyHostCount` — 일부 task만 죽은 상황

### 10.4 이 조합에서 특히 자주 터지는 것

| 상황 | 증상 | 원인 | 조치 |
|---|---|---|---|
| 오토스케일 후 DB 장애 | task 증가 직후 커넥션 에러 | 총 커넥션 = task × 풀 | 풀러 도입, 최대 task 제한 (§10.2) |
| 축소마다 5xx 스파이크 | 스케일인 시점 에러율 | 그레이스풀 셧다운 부재 | §10.3(d) |
| CPU 낮은데 느림 | 사용률 40%, p95 상승 | 이벤트 루프 포화 | lag p99로 판단 (§10.1) |
| 배포 후 서서히 느려짐 | 시간이 갈수록 지연 증가 | 메모리 누수·핸들 누수 | heap 추세 + 프로파일링 |
| 특정 API만 느림 | 한 엔드포인트의 p95만 상승 | N+1 쿼리 | 트레이스의 쿼리 span 수 확인 (§9.1) |

한 화면에 전부 넣으면 아무것도 읽히지 않습니다. 보는 사람과 시점으로 나눕니다.

| 층 | 이름 | 대상 | 패널 수 | 내용 |
|---|---|---|---|---|

| 2 | **Scaling Decision** | 용량 판단 | 10 이내 | §3 결정 트리 지표를 나란히: in-flight/한계, 풀 대기, 런타임 포화, 큐 기울기, throttling, 자원 상한 |

집계 그래프는 이 상황을 구조적으로 감춥니다.
