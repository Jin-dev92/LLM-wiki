## Express 레거시 파악·이관 규칙

> 레거시를 **개선하기 위한** 규칙이 아니라 **정확히 읽고 옮기기 위한** 규칙이다.
> 이관 전략 자체는 [[strangler-fig-migration]], 도착지 규칙은 [[rules/stacks/nestjs]] 참조.

### 0. 대원칙 — 이관 전에는 건드리지 않는다

- 레거시 코드는 **읽기 전용**으로 취급한다. 리팩터링·포맷·타입 추가를 곁들이지 않는다.
- 이유: 이관 후 동작 비교의 기준선이 흔들린다. "옮기면서 고쳤다"는 버그의 원인 추적을 불가능하게 만든다.
- 레거시에서 발견한 버그는 **고치지 말고 기록**한다. 이관 시 의도적으로 재현할지 말지를 따로 결정한다.
- 예외: 이관을 막는 보안 취약점. 이 경우 별도 PR로 분리한다.

### 1. 라우트 인벤토리부터 만든다

코드를 읽기 전에 **표면적(surface)을 먼저 확정**한다. 이게 이관 완료의 정의가 된다.

각 라우트에 대해 다음을 기록한다.

| 항목 | 왜 필요한가 |
|---|---|
| 메서드 + 경로 | 이관 단위이자 컷오버 단위 |
| 인증/인가 방식 | 미들웨어에 숨어 있어 라우트 코드만 보면 안 보인다 |
| 실제 호출 여부 | 액세스 로그로 확인. **죽은 라우트는 옮기지 말고 폐기**한다 |
| 응답 형태 | 에러 응답 형태가 라우트마다 다른 경우가 흔하다 |
| 외부 의존성 | 이관 시 장애 대응 정책이 필요한 지점 → [[rules/stacks/resilience]] |

> **죽은 라우트 폐기가 가장 큰 절감이다.** 이관 범위를 줄이는 것이 이관을 빠르게 하는 유일한 확실한 방법이다.

### 2. 미들웨어 체인을 명시적으로 펼친다

Express의 핵심 난점은 **동작이 라우트 핸들러가 아니라 등록 순서에 있다**는 점이다.

- `app.use(...)` 전역 미들웨어, 라우터 단위 미들웨어, 라우트 인자 미들웨어를 **등록 순서대로** 나열한다.
- 순서 의존 동작을 찾는다 — body 파싱, CORS, 세션 로드, 트랜잭션 시작, 로깅.
- NestJS로 옮길 때 각 미들웨어가 무엇에 대응하는지 판정한다.

| Express | NestJS |
|---|---|
| 인증 미들웨어 | Guard |
| 요청/응답 변환 | Interceptor |
| 입력 검증 | Pipe (class-validator DTO) |
| 에러 핸들러 | Exception Filter |
| 그 외 횡단 관심사 | Middleware 또는 Interceptor |

### 3. 암묵적 인증·세션을 추적한다

- `req.user`·`req.session`이 **어디서 채워지는지** 추적한다. 라우트 코드에는 채우는 곳이 없다.
- 세션 저장소(메모리·Redis·DB)를 확인한다. **이관 중 두 서버가 세션을 공유해야 하는지**가 여기서 결정된다.
- JWT면 서명 키·만료·클레임 구조를 기록한다. 신구 서버가 같은 토큰을 검증해야 한다.

### 4. 에러 처리 관례를 파악한다

- Express 레거시는 보통 **에러 응답 형태가 통일되어 있지 않다**. 라우트별 실제 응답을 수집한다.
- `next(err)`로 넘기는 경로와 `res.status().json()`으로 직접 응답하는 경로를 구분한다.
- **클라이언트가 의존하는 형태를 그대로 유지**한다. 이관은 계약 변경이 아니다. 응답 형태 통일은 이관 완료 후 별도 작업으로 뺀다.

### 5. 이관 단위 판정

라우트 하나씩이 아니라 **함께 움직여야 하는 묶음**으로 자른다.

- 같은 테이블에 쓰는 라우트들은 함께 옮긴다 — 신구 서버가 같은 테이블에 동시 쓰기를 하면 트랜잭션 경계가 사라진다.
- 세션·캐시를 공유하는 라우트들도 함께 옮긴다.
- 읽기 전용 라우트가 가장 안전한 첫 이관 대상이다.

### 6. 이관 검증

- 이관한 라우트는 **레거시와 신규의 응답을 실제로 비교**한다(섀도 트래픽 또는 응답 diff).
- 비교 없이 "코드를 옮겼으니 같다"고 판단하지 않는다. 미들웨어 순서·기본값·타입 강제 변환에서 차이가 난다.
- 검증 코드는 남긴다 → [[spec-as-code]]

## 배경/이유
- 신규 회사 레거시(Express + MySQL) → NestJS + PostgreSQL 이관 대비. 레거시를 "읽는 규칙"이 없으면 이관이 곧 재작성이 되고, 재작성은 회귀를 부른다.
