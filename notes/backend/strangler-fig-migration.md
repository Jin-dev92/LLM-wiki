## 핵심

레거시 시스템 앞에 **라우팅 계층**을 두고, 기능을 하나씩 신규 시스템으로 옮기면서 해당
경로만 신규로 흘려보낸다. 옮겨진 기능은 레거시에서 제거된다. 모든 경로가 이전되면 레거시는
호출자가 없어져 저절로 죽는다. 무화과나무가 숙주를 감싸 고사시키는 모습에서 온 이름이다.

빅뱅 재작성과의 차이는 **되돌릴 수 있는 단위로 쪼갠다**는 점 하나다. 라우트 하나를 옮기고
문제가 생기면 그 라우트만 레거시로 되돌린다.

## 상세

### 왜 빅뱅 재작성이 아닌가

- 재작성 기간 동안 **레거시에 들어가는 변경이 멈추지 않는다.** 두 벌을 동시에 유지하게 되고, 격차는 시간에 비례해 벌어진다.
- 완료 전까지 **가치가 0**이다. 중간에 중단되면 남는 게 없다.
- 회귀를 한꺼번에 마주친다. 스트랭글러는 회귀를 라우트 단위로 분산시킨다.

### 라우팅 계층을 어디에 두는가

세 위치 중 하나. 뒤로 갈수록 세밀하지만 운영 부담이 크다.

1. **리버스 프록시(nginx/ALB)** — 경로 패턴으로 분기. 배포 없이 룰만 바꿔 롤백 가능. 가장 단순하고 대부분 여기서 충분하다.
2. **레거시 안에서 프록시** — Express에 미들웨어를 붙여 특정 라우트를 신규로 포워딩. 레거시 배포가 필요하지만 요청 컨텍스트(세션 등)를 쓸 수 있다.
3. **API 게이트웨이** — 헤더·사용자 속성 기반 분기, 카나리 비율 조절까지. 이미 게이트웨이가 있을 때만.

### 진짜 난점은 라우팅이 아니라 데이터다

라우팅 분기는 쉽다. 어려운 건 **전환 기간 동안 두 시스템이 같은 데이터를 본다**는 것이다.

- **같은 DB를 공유하는 기간**을 둘 것인가. 두면 이전은 쉽지만 스키마를 바꿀 수 없다(레거시가 깨진다).
- 별도 DB로 가면 **동기화 방식**을 정해야 한다 — 듀얼 라이트(애플리케이션이 양쪽에 쓴다, 정합성 깨지기 쉬움) vs CDC(변경 데이터 캡처, 복잡하지만 안전).
- 트랜잭션 경계가 두 시스템에 걸치면 **원자성이 사라진다.** 함께 써야 하는 테이블을 건드리는 라우트들은 반드시 한 묶음으로 옮긴다 → [[rules/stacks/express-legacy]] §5.

MySQL → PostgreSQL 이전이 겹치면 타입·시퀀스·격리수준 차이가 여기에 얹힌다 → [[rules/stacks/postgres]].

### 컷오버 단위와 순서

- **읽기 전용 라우트부터.** 잘못돼도 데이터가 깨지지 않는다.
- 그다음 **독립적인 쓰기 라우트**(다른 기능과 테이블을 공유하지 않는 것).
- **인증·세션은 가장 늦게.** 전 라우트가 의존하므로 먼저 옮기면 롤백 단위가 전체가 된다. 대신 전환 기간 내내 **신구 서버가 같은 토큰/세션을 검증할 수 있게** 만들어 둔다.
- 죽은 라우트는 옮기지 않고 폐기한다. 이관 범위를 줄이는 게 가장 확실한 가속이다.

### 롤백 기준을 미리 정한다

컷오버마다 되돌릴 조건을 **숫자로** 정해두지 않으면, 장애 중에 판단하게 된다.

- 에러율·p99 지연의 임계치와 관측 창(예: 15분)
- 되돌리는 방법과 소요 시간 — 프록시 룰 원복으로 끝나는지, 데이터 되돌림이 필요한지
- 데이터를 이미 신규 쪽에만 쓴 경우의 복구 경로

### 검증

옮긴 라우트는 **레거시와 신규의 응답을 실제로 비교**한다. 섀도 트래픽(복제 요청을 신규에
보내되 응답은 버림)이 가장 안전하다. 코드를 옮겼다는 사실은 동치성의 근거가 아니다.
비교 코드는 일회성으로 버리지 말고 남긴다 → [[spec-as-code]]

## 작업 경계

**DB 이관(스키마·데이터 이전, 컷오버)은 사람이 직접 수행한다.** 이 노트는 전환 *전략*을
판단하기 위한 것이지 AI에게 실행을 맡기기 위한 것이 아니다. AI가 맡는 범위는 이관 이후의
애플리케이션 코드와, 라우트 이관·검증 같은 코드 작업이다.

**AI의 DB 접근은 읽기 전용 계정으로만 준다.** 레거시 스키마·데이터를 조회해 이관 대상을
파악하는 데는 유용하고, 쓰기는 계정 권한으로 막힌다. 문서상의 금지가 아니라 권한이
경계선이 되도록 한다.

> 아래가 확정되기 전에는 전환 계획을 세우지 않는다.

- 트래픽 규모와 피크 패턴 — 섀도 트래픽·듀얼 라이트의 비용이 여기서 갈린다
- 배포 단위: 모놀리스인가, 이미 쪼개져 있는가
- 다운타임 허용치 — 0이면 데이터 이전 방식이 CDC로 강제된다
- 인증 방식(JWT/세션)과 세션 저장소 — 신구 공존 가능 여부
- 앞단에 이미 리버스 프록시·게이트웨이가 있는가
- 레거시에 회귀 테스트가 있는가 — 없으면 섀도 비교가 유일한 안전망이다
- 이관 중에도 레거시에 기능 추가가 계속되는가(대부분 그렇다)
