## 요약
5년차부터는 "성실·열정"이 무의미하고, **"어떤 문제를 어떻게 풀었는지가 7초~10분 안에 읽혀야"** 한다.
가장 치명적 탈락 사유는 회사·기간·직책만 있고 **무엇을 했는지가 없는** 이력서. 성과는 Before→After 수치로,
성공만이 아닌 **문제 상황→대처**까지, 기술스택은 나열이 아니라 **문제와 연결**, 핵심 경험 2~3개에 집중.

### 채용담당자의 시간순 검토 흐름
- **1차 스캔 7.4초**: 직무 키워드 매칭, 연차, 레이아웃 — "계속 볼지" 결정. → 상단에 핵심 임팩트 노출 필수.
- **2차 검토 ~10분**: 프로젝트별 역할/기여도, 성과 수치, 기술스택↔경험 연결성.
- **3차**: GitHub/포트폴리오 클릭 → 코드 품질, README 정리 상태.

### 결정적 탈락 요인
1. **내용 없음**(최악): 기간·회사·타이틀만, 무엇을 했는지 빠짐 → 의사소통 능력 의심, 1순위 드롭.
2. 뻔한 형용사형 자기소개("열정적·성실한") → 평가 불가능한 빈 문장.
3. 기여도 안 보이는 팀 프로젝트("3명이서 진행") → 본인 역할/비중 불명 → 보수적 탈락.
4. 회사/직무 이해 부족 지원동기(어느 회사에나 붙는 문장).
5. 정리 안 된 GitHub 링크(README·커밋 없는 레포 노출) → "관리 안 됨" 인상.
6. 시장 구조 요인(상시채용 소수 TO·기술 공급과잉·채용 위축) — 이력서 문제와 구분할 것.

### 합격 이력서의 공통점
- 성과는 **Before→After** 구조(수치 애매한 경험도 전후 변화로). 예: 온보딩 문서 정비로 적응기간 3주→1주.
- 잘한 것 나열 X, **문제 상황→분석→대처**를 포함(대응 능력이 핵심 평가점).
- 기술스택은 JD 매칭용으로 보이되 **각 기술이 어떤 문제 해결에 쓰였는지** 연결.
- **핵심 경험 2~3개 집중**, 직무 무관 프로젝트는 뒤로/제외.
- 가독성: 비개발 인사담당자도 이해하게, 이력서는 큼직하게 + 상세는 별도 경력기술서로 분리.
- GitHub는 **선별된 포트폴리오**(README 1~2줄+스택, 노출 레포 3~5개 고정, 나머지 private).

### 5년차 체크리스트(요지)
역할+기여도+Before/After 수치 / 차별화 경험(예: Claude Code 자동화 PR 리뷰)을 상단 노출 /
소규모 팀 경험을 "책임 범위"로 서술 / 기술스택↔문제해결 1줄 연결 / JD 키워드 명시 매칭 /
GitHub 정리 / 회사별 구체 지원동기 / 7~10분 내 읽히는 분량.
