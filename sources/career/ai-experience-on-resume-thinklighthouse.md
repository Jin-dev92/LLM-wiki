## 요약
8분 29초 손그림(화이트보드) 영상. 자막이 화면에 구워져 있어 watch 스킬로 80프레임 전체를 읽어 추출(yt-dlp 자막은 429, Whisper는 로컬 SSL 오류로 실패 → 프레임 기반).

핵심 주장: 이력서에 `"Claude를 활용해 개발했습니다"`, `"Codex로 생산성을 높였습니다"`처럼 **도구를 썼다는 사실**을 적는 건 이제 변별력이 없다(오히려 마이너스가 될 수 있다). 면접관이 보는 건 *AI를 썼는지*가 아니라 **AI가 안전하게 일할 수 있는 개발 환경을 어떻게 설계·통제했는지**다. 거창한 대기업 프로젝트가 아니라 Spring Boot 토이 프로젝트 하나라도 "AI 시대 개발 프로세스를 직접 설계"한 경험으로 만들 수 있다.

3가지 원칙 + 그대로 복붙하라고 제시한 이력서 문구:

1. **바로 구현 X → 계획 → 사람 승인** — `"회원가입 API 만들어줘"`처럼 바로 시키면 AI가 의도하지 않은 파일·기존 API 응답 포맷까지 건드린다. "구현하지 말고 기존 구조 파악 후 작업 계획과 리스크만 정리해줘" → 사람이 승인한 뒤 구현.
   - 문구: *"AI 코드 생성 시, 작업 범위 이탈 및 변경 리스크 방지를 위한 plan-first workflow와 human approval gate를 적용해 개발 안정성 향상"*
2. **AI를 역할별로 분리** — 하나의 AI에 조사·구현·리뷰를 다 시키지 말 것. 회사에 기획자/개발자/리뷰어/QA가 따로 있듯. Planner는 구현 순서·계획만, Reviewer는 직접 고치지 않고 문제점만 지적(리뷰어가 고치면 그건 또 하나의 구현).
   - 문구: *"Researcher, Planner, Reviewer 역할을 분리한 AI 개발 워크플로우를 구성해 구현과 검증 과정을 독립적으로 운영"*
3. **프롬프트·도구 사용 로그 남기기**(발표자가 가장 강조) — 결과물만 있고 어떤 질문을 했는지·AI가 어떤 파일을 읽었는지 기록이 없으면 문제 발생 시 원인 추적 불가. AI 작업을 블랙박스로 두지 않는 것.
   - 문구: *"Prompt 및 logging hook을 구축해 AI agent 작업의 재현성 및 오류 원인 추적 가능성 향상"*

마무리: "AI 써봤다"는 점점 변별점이 아니게 되고, **무엇을 통제했고 어떻게 품질을 높였는지** 말할 수 있는 사람이 강해진다.
